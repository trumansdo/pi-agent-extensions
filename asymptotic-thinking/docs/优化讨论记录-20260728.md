## 三、讨论过程摘要

### 第1轮：对 java-dev.ts HINT 的评估

**问题点：** 当前 HINT = `"关注JVM生态、Spring约定、类型与泛型安全"`

| 条目 | 诊断 | 结论 |
|:--|:--|:--|
| `关注JVM生态` | 语义发散，模型无法据此收敛行为 | ❌ 负收益，应删 |
| `Spring约定` | 框架偏见，对非Spring项目产生误导 | ❌ 负收益，应删 |
| `类型与泛型安全` | Java语言独有特征，表述偏弱 | ✅ 保留并改写为指令形式 |

**建议替代：** `"显式标注泛型类型参数 · 权衡checked/unchecked异常策略"`

### 第2轮：对全部通用流程指令的分析

分析了 `templates.ts` 中4个状态（DEEP_UNDERSTAND / DESIGN / EXECUTE / VERIFY）的通用 actions + constraints 块，这些内容**全部27个子类型×6个难度共享，一模一样**。

**发现的问题汇总：**

| 问题类型 | 例子 | 影响 |
|:--|:--|:--|
| 口语化负向约束 | `不要见路就走`、`不即兴`、`不抽象` | 模型对"不要X"执行强度低于"要Y" |
| 模糊副词 | `必要时`、`深度分析` | 模型可能跳过或不量化执行 |
| 语义冗余 | 子类型 buildPrompt 和通用 actions 重复同一套话 | ~50%字符是重复内容 |
| 无意义引导 | `利用最适合的工具和模式`（模型自动会选）| 纯浪费token |
| 上下文脱节 | `考虑团队标准`（LLM不知道你的团队）| 无效指令 |

**建议精简幅度：** 通用块从 ~710字符 → ~345字符（-51%）

## 四、通用流程指令优化方案（讨论稿）

### DEEP_UNDERSTAND 通用块

**当前（~180字符）：**
```
- 深度分析用户需求细节（功能/边界/约束/验收标准）
- 识别隐含需求和潜在歧义，主动确认而非猜测
- 必要时从本地 mempal 或外部网络检索相关信息
- 可读文件辅助理解，不执行修改
- 不要见路就走、不要盲目执行
- 完成后调用 asymptotic-think_transition 流转到 DESIGN 或 EXECUTE
```

**建议（~80字符）：**
```
- 逐条列出需求的功能边界、约束条件和验收标准
- 缺失信息用工具检索补齐
- 只读文件辅助理解，不执行写操作
- 完成 → 流转 DESIGN
```

### DESIGN 通用块

**当前（~130字符）：**
```
- 设计完整的实施路径和工具组合
- 考虑技术选型、架构规范、团队标准
- 方案需包含涉及文件/前置依赖/步骤/验收标准
- 方案必须具体可执行、不抽象
- 设计完成前不执行
```

**建议（~70字符）：**
```
- 方案含：涉及文件 → 前置步骤 → 实施路径 → 验收标准
- 每个步骤写明具体工具名和文件路径
- 设计完成前不执行代码
```

### EXECUTE 通用块

**当前（~130字符）：**
```
- 严格按方案执行，不偏离不即兴
- 每步执行后先自检再继续
- 利用最适合的工具和模式
- 方案不可行时重新设计，不强行推进
- 达成目标后调用 asymptotic-think_transition 流转到 VERIFY
```

**建议（~55字符）：**
```
- 严格按方案步骤执行，每步自检后再推进
- 方案不可行 → 回退 DESIGN 重新设计
- 完成 → 流转 VERIFY
```

### VERIFY 通用块

**当前：4维检查表 + 3条action**
```
| 完全理解指令全部内容 | ✅/❌ | ... |
| 精准逐字执行，不增不减 | ✅/❌ | ... |
| 完整完成所有要求 | ✅/❌ | ... |
| 输出格式符合规范 | ✅/❌ | ... |
```

**问题：** 前两维（理解指令 ↔ 精准执行）和第三维（完整完成）语义重叠。

**建议：改为3维正交检查表**
```
| 需求理解正确完整     | ✅/❌ | ... |
| 实施步骤全部完成     | ✅/❌ | ... |
| 输出格式符合规范     | ✅/❌ | ... |
```
actions 精简为：
```
- 有 ❌ 项修正后全部重新验证
- 全部 ✅ → 流转 IDLE
```

## 五、子类型专属指令优化方向（待讨论）

在通用流程精简的基础上，每个子类型（如 java-dev.ts）的 `buildPrompt()` 应**只输出该语言/任务类型独有的增量指令**，不再重复通用流程。

### 当前问题

以 java-dev.ts EXECUTE 为例，子类型输出和通用块严重重复：

```
子类型 buildPrompt(EXECUTE):
  严格按方案执行：不偏离方案、不即兴发挥 → 错误分析根因后修正
  → 每步执行后自检再继续 → 完成目标后 TRANSITION 进入 VERIFY。

通用 actions(EXECUTE):
  - 严格按方案执行，不偏离不即兴
  - 每步执行后先自检再继续
  - 利用最适合的工具和模式
  ...

通用 constraints(EXECUTE):
  - 达成目标后调用 TRANSITION 流转到 VERIFY
```

**两处完全重复。**

### 建议方向

子类型只输出该任务类型的**语义约束增量**，例如 Java 开发：

```
DEEP_UNDERSTAND:
  明确技术栈（纯Java/Spring Boot/Android/其他）及JDK版本
  → 识别类型层级与泛型约束
  → 评估异常策略（checked/unchecked）与null安全处理

EXECUTE:
  警惕NPE风险点 · 泛型类型标注完整 · 异常处理策略一致

VERIFY:
  无raw type · 异常处理策略一致 · null安全处理到位
```

## 九、提示词指令编写原则·外部参考（2026/7/28 09:10）

> 检索来源：Lilian Weng's Blog / PromptingGuide.ai / OpenAI Best Practices
> 聚焦：正向指令、减少口语化、指令化/规则化

### 核心原则汇总

| 原则 | 来源 | 说明 |
|:--|:--|:--|
| **正向指令替代负向约束** | Lilian Weng, PromptingGuide, OpenAI | "avoid saying what not to do but say what to do instead" |
| **具体精确，避免模糊** | Lilian Weng, PromptingGuide | 用具体格式/数量/步骤替代"必要时""适当"等模糊副词 |
| **简洁直接** | PromptingGuide | 越直接越有效，不要过度聪明地包装指令 |
| **指令前置 + 分隔符** | PromptingGuide | 指令放在 prompt 开头，用 `###` 或 XML 标签分隔 |
| **迭代优化** | PromptingGuide, Lilian Weng | 从简单开始，逐步增加约束，实验驱动 |
| **示例驱动** | OpenAI | 提供期望格式的示例比纯文字描述更有效 |

### 正向指令 vs 负向约束（关键对比）

**Lilian Weng（2023.3）：**
> "When interacting with instruction models, we should describe the task requirement in details, trying to be specific and precise and **avoiding say 'not do something' but rather specify what to do**."

**PromptingGuide.ai：**
> "Another common tip when designing prompts is to **avoid saying what not to do but say what to do instead**. This encourages more specificity and focuses on the details that lead to good responses from the model."

**OpenAI 示例对比：**

| ❌ 负向约束 | ✅ 正向指令 |
|:--|:--|
| `DO NOT ASK USERNAME OR PASSWORD. DO NOT REPEAT.` | `The agent will attempt to diagnose the problem and suggest a solution, whilst refraining from asking any questions related to PII. Instead of asking for PII, refer the user to the help article...` |
| `The description should be fairly short, a few sentences only, and not too much more.` | `Use a 3 to 5 sentence paragraph to describe this product.` |

### 对本项目的直接启示

当前讨论记录中识别的问题与外部最佳实践高度吻合：

| 当前问题 | 外部原则 | 改造方向 |
|:--|:--|:--|
| `不要见路就走`、`不即兴`、`不抽象` | 正向指令替代负向约束 | 改为 `逐条列出需求`、`严格按方案步骤执行`、`方案含具体文件路径` |
| `必要时`、`深度分析` | 具体精确，避免模糊 | 改为 `缺失信息用工具检索补齐`、`逐条列出功能边界/约束/验收标准` |
| `利用最适合的工具和模式` | 简洁直接，删除无意义引导 | 直接删除（模型自动会选） |
| `考虑团队标准` | 避免上下文脱节 | 删除（LLM 不知道你的团队） |
| 口语化表述（`不要见路就走`） | 指令化/规则化 | 改为结构化指令格式 |

## 十、生命周期事件与提示词分工（2026/7/28 09:30）

> 澄清：pi-agent 有两个生命周期事件，提示词职责不同

### 事件模型

```
pi-agent 生命周期
│
├─ before_agent_start（触发 1 次）
│   └─ 职责：分析任务 → 输出 tool_call 参数 → 设定画像
│   └─ 不涉及三层架构
│
└─ turn_end（每轮触发，多轮递进）
    └─ 职责：渐近式思考的五态流转
    └─ 第1/2/3层架构的作用域
```

### before_agent_start 提示词

目标：① 以理解指令的任务类型和难度为最高原则 ② 必须输出 tool_call 参数

```xml
<xml role="严格遵守人格角色定义" desc="渐近式思考：启动">
<instruction spec="markdown">
- 深入分析用户指令的任务类型和难度
- 输出内容中必须包括调用 asymptotic-think_set-task-info 工具的信息
- 以用户指令和数据为主，不可擅自覆盖
</instruction>
</xml>
```

### turn_end 提示词（三层架构作用域）

第1层通用指令精简方向（沿用讨论记录第四节方案）：

| 状态 | 精简后 |
|:--|:--|
| DEEP_UNDERSTAND | 逐条列出功能边界/约束/验收标准 · 缺失信息检索补齐 · 只读不写 · 完成流转 DESIGN |
| DESIGN | 方案含：涉及文件→前置步骤→实施路径→验收标准 · 每步写明工具名和路径 · 设计完成前不执行 |
| EXECUTE | 严格按方案步骤顺序执行 · 每步自检后推进 · 方案不可行回退 DESIGN · 完成流转 VERIFY |
| VERIFY | 3维检查表（需求理解/步骤完成/格式规范）· 有❌修正后全部重验 · 全部✅流转 IDLE |

### 职责边界

| | before_agent_start | turn_end |
|:--|:--|:--|
| 触发次数 | 1 次 | 每轮 |
