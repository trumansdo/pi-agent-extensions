## 第一部分：背景与总览

### 1.1 四大优化目标

| 目标 | 问题 | 方向 |
|:--|:--|:--|
| **① 指令服从性** | 模型"不听话"：流转指令措辞过软、位置不佳、通道错位 | 命令化措辞 + 前置 + 数据/指令分离 |
| **② 前缀缓存最大化** | DeepSeek 缓存要求请求序列纯递增；需避免"注入不入史"通道 | 纯递增铁律（全部入史、只增不删） |
| **③ 输出 token 最小化** | 输出冗余消耗 token；目标是以最高缓存率为标准，也以减少输出为目的，但不能让质量下降 | 引导要求"输出精简文字但不丢失内容"；END 极简；验证表紧凑 |
| **④ 状态机语义清晰** | IDLE 承担"启动 + 结束"双职责，语义模糊 | START/END 拆分 + before_agent_start 自动转换 |

### 1.2 核心设计原则（三条主线）

1. **纯递增**：所有进入请求序列的消息必须入史，不存在"只注入不入史"的合法通道。
2. **流程纪律随难度递增**：简单任务流程宽松（防空转），复杂任务流程严格（防跑偏）——主体是已有状态集开放机制（`getAllowedTargets`），提示词做配套。
3. **状态单一职责**：START 只负责启动初始化，END 只负责任务终结。

## 第二部分：指令强化与缓存优化

### 2.1 现状架构（三层结构）

```
用户消息
  │
  ├─ before_agent_start（每轮用户消息时触发 1 次）
  │     └─ 注入完整 XML 引导（状态行 + 领域提示 + actions + constraints）→ 入史
  │
  ├─ tool_result（每次工具执行）
  │     └─ 返回流转结果 + 新状态完整引导 + 指令性文字（数据/指令混杂）→ 入史
  │
  └─ turn_end（每轮结束触发）
        └─ 轮次计数 + 超限警告 + 状态提醒（steer 注入）→ 入史
```

**已核实**：全部注入通道均通过 `message_end` 事件写入会话历史，序列严格只增不删，当前无违反纯递增的通道。

**关键机制（工具循环内约束的真实通道）**：turn_end 的 steer 消息经 steering 队列，在**工具批次后、下一轮 LLM 推理前**注入，位置在请求**末尾**（recency 最强）、user 通道（服从性最高）、入史（纯递增兼容）。**工具循环内每次推理前模型都会看到它**——时机已被覆盖，问题在措辞强度。

### 2.2 根因诊断（四缺口）

| 缺口 | 具体表现 | 后果 |
|:--|:--|:--|
| **措辞过软（核心）** | turn_end 提醒是陈述句（"第N/M轮"状态行），无"必须/禁止"命令语；引导中流转指令也是"完成后调用" | 模型把状态机约束当背景而非命令，工具循环内跑偏时拉不回来 |
| **位置不佳** | 流转指令埋在引导 actions 末尾 | 用户消息轮次中，模型读完前半段就动手，看不到最后的流转指令 |
| **通道错位** | tool_result 夹带指令性文字；tool_result 通道的指令服从性最低 | 指令被当数据处理，污染数据纯度 |
| **缓存风险** | 若引入 context 类"注入不入史"通道将违反纯递增（当前无此通道） | 注入的守卫永不命中缓存，且使完整匹配在该点断裂 |

### 2.3 优化方案（指令/缓存部分）

#### 优化 1：turn_end 强烈提醒 + 违规检测（核心）

**文件**：`src/index.ts`（turn_end 钩子）

- 非 END 时每轮 steer 内容改为 must/never 命令语：
  ```
  <stateGuard>
  渐近式思考·强制执行：当前处于【X】状态（第N/M轮）。
  本阶段必须完成该状态职责后，调用 asymptotic-think_transition 流转状态。
  未调用 asymptotic-think_transition 前，请勿结束回复；若阶段未完成请说明原因后继续推进。
  </stateGuard>
  ```
- 违规检测：检查 `event.toolResults` 是否含 `TOOL_TRANSITION`；未调用时追加 `<violationWarning>`。
- **超限分级**：
  - `turnCount > maxTurns`：第一级——警告"已超过上限（N>M），请立即流转"
  - `turnCount > maxTurns + max(1, ceil(maxTurns/3))`（超 1/3 缓冲）：第二级——**强制停止**：
    ```
    <hardStop>⛔ 强制停止：你已在【X】状态停留 N 轮（上限 M），严重超时。
    立即停止当前所有操作——禁止继续执行工具调用、禁止继续输出内容。
    必须调用 asymptotic-think_transition 流转状态，或等待用户指令。</hardStop>
    ```

#### 优化 2：tool_result 数据/指令分离

**文件**：`src/index.ts`（TOOL_TRANSITION.execute）

- content 只返回数据：`✅ 状态流转成功：从【A】到【B】，第N/M轮。允许下一步：...`
- 删除指令性文字；删除新状态完整 XML 引导（由 transition tool_result 自身 + before_agent_start 提供）。

#### 优化 3：引导指令强化（前置 + must 措辞）

**文件**：`src/templates.ts`

1. 阶段目标前置：`<instruction>` 状态行后插入"本阶段必须调用 transition 流转"声明。
2. actions 措辞升级：“完成后调用”→“必须调用（强烈要求，未流转请说明原因）”。

#### 优化 4：不引入 context 钩子与静态守卫

- **context 钩子**：注入不入史 → 违反纯递增 → 永不命中缓存 → **否决**。
- **静态守卫入史**：位置在历史中间、recency 弱、不解决工具循环问题 → **不采用**。

## 第三部分：状态机重构 START/END

### 3.1 动机（IDLE 双职责）

IDLE 同时承担"启动初始化"与"结束终态"，任务完成后用户再发消息时无法区分"已结束"与"待开始"。

**决策（已确认）**：IDLE 完全移除，用 START + END 取代。核心逻辑：

> 只要用户发消息，`before_agent_start`（用户发送消息后的第一个钩子）必然触发 → 自动进入 START；用户不发消息则无会话，IDLE 无存在意义。

### 3.2 新状态机

```
START → DEEP_UNDERSTAND → DESIGN → EXECUTE → VERIFY → END
   ↑                                                     │
   └──────────── before_agent_start 自动转换 ─────────────┘
```

| 状态 | 职责 | 触发 |
|:--|:--|:--|
| START | 新任务起点：评估任务复杂度 → 决定直接回答或启动流程（set-task-info） | before_agent_start 检测 END（或会话初始）时自动进入 |
| DEEP_UNDERSTAND / DESIGN / EXECUTE / VERIFY | 不变 | transition |
| END | 任务终态 | VERIFY 完成后 transition |

### 3.3 关键机制（已确认）

1. **before_agent_start 判断语义**：
   - `state === "END"` **或 `state` 为空（null / 未初始化，新建会话）** → 代码自动 transition 到 START → 注入 START 引导（**新任务开始**）
   - `state !== END` 且非空（DEEP_UNDERSTAND/DESIGN/EXECUTE/VERIFY 等）→ **保持当前状态，不转 START**，注入续作提醒 —— 语义：**上一轮任务未正常完成，或需要多轮对话推进，不可中断**
2. **END 不允许手动 transition**：只能靠 before_agent_start 代码转换。
3. **画像清空时机** = 转入 END 时（原"回到 IDLE 清空"迁移）。
4. **任务轮次计数** = 从 START 出发 +1（原"从 IDLE 出发"迁移）。

## 第四部分：全链路路径感知（已确认）

> **升级（2026/8/1 用户拍板）**：从"补位一句"升级为"**全链路感知**"——根据已走过的状态（`visited`）**动态生成适配的提示词**，而非标准提示词 + 尾部补救。可行性评估：容易（visited 数据已就绪 + pathAdapter 纯函数组合，约半天工作量）。

### 4.1 问题场景

状态集开放（`getAllowedTargets`）允许 TRIVIAL/SIMPLE 跳过前置状态，但**被跳过状态原本应产出的内容没有消失**：

| 场景 | 断档表现 |
|:--|:--|
| TRIVIAL 直达 EXECUTE（跳 DEEP_UNDERSTAND + DESIGN） | EXECUTE 提示词说"按方案步骤执行"——但方案不存在 |
| SIMPLE 跳 DEEP_UNDERSTAND 到 DESIGN | DESIGN 提示词说"列方案"——但需求要点未明确 |

**补位方案的问题**：标准提示词 + 尾部补一句 → 自相矛盾（前说"按方案执行"后说"没方案"）。

### 4.2 解法：全链路感知（组合式 pathAdapter）

提示词 = **基础模板（不动） + 路径适配段（pathAdapter 按 visited 生成）**：

```ts
// buildTemplate 增加 visited 参数
buildTemplate(state, turn, master, sub, diff, visited):
  prompt = baseTemplate(state, master, sub, diff)   // 现有模板不变
  prompt += pathAdapter(state, visited)              // 路径适配段
  return prompt

// pathAdapter：纯函数（state + visited → 字符串），可单测
function pathAdapter(state, visited) {
  // 直达 EXECUTE：无前置理解/设计
  if (state === "EXECUTE" && !visited.includes("DESIGN"))
    return "\n> 本任务直达执行模式：未经过深度理解与方案设计。请先自行明确需求要点与执行步骤，再直接实施。";
  // 跳理解到 DESIGN
  if (state === "DESIGN" && !visited.includes("DEEP_UNDERSTAND"))
    return "\n> 本任务未经过深度理解。请先简要明确需求边界，再列出方案。";
  // 回退到 DESIGN（曾到过 EXECUTE）
  if (state === "DESIGN" && visited.includes("EXECUTE"))
    return "\n> 曾进入 EXECUTE 后回退。方案需覆盖已执行部分的调整与修正。";
  return "";  // 全流程：无适配段
}
```

**路径形态枚举**（由难度决定，有限 4 类）：全流程 / 直达执行（TRIVIAL）/ 跳理解（SIMPLE）/ 回退重做。

### 4.3 实现（轻量）

| 改动 | 内容 |
|:--|:--|
| `SessionState` 增字段 | `visited: ThinkingState[]`（本次任务经过的状态，转入 END 时清空） |
| `transition()` 记录 | 每次流转把 `to` push 进 `visited` |
| `session-store` 持久化 | 建表增 `visited TEXT` 列（JSON 字符串；空数组存 NULL）；旧库 `ALTER TABLE ADD COLUMN` 幂等迁移；`serializeVisited`/`parseVisited` 序列化（脏数据安全降级 []） |
| `templates.ts` 新增 `pathAdapter` | 纯函数（state + visited → 适配段），约 30 行，可单测 |
| `buildTemplate` 接收 | 增加 `visited` 参数，基础模板 + pathAdapter 组合 |

**工作量**：pathAdapter ~30 行 + 调用处 ~5 行 + visited ~5 行 ≈ 半天。

## 第六部分：难度自适应措辞（方向 A/C/D）

> **状态更新（2026/8/1 用户拍板）**：
> - ❌ **方向 A 取消**（事前"如实评估难度"措辞会诱导模型走最短路径，风险大于收益）
> - ❌ **方向 C 取消**（TOOL_TRANSITION 已告知合法目标状态，统一"必须流转"措辞足够，分档反而给偷懒借口）
> - ✅ **方向 D 已实施**（放开超限重估 + 三档文案分级，见下）

### 方向 D：超限警告按难度分级（已实施）

**机制改动**：`setTaskInfo` 允许**状态超限时重新评估难度**（原仅 START 可调）——防御难度虚高导致的空转。

```ts
// state-machine.ts setTaskInfo
const overLimit = current && state !== null && state !== "END"
  ? current.stateTurnCount > getMaxStateTurns(state, current.difficulty)
  : false;
if (state !== "START" && !overLimit) {
  return { ok: false, reason: "仅可在 START 阶段或状态超限时设定任务信息" };
}
```

**文案分级**（bumpAndWarn 三档 × 三级，已实施 + 单测）：

| 阈值 | TRIVIAL/SIMPLE（温和） | MODERATE（标准） | COMPLEX+（严厉） |
|:--|:--|:--|:--|
| 软提醒 | 提示可重估难度 | 尽快完成并流转 | 强调流程纪律 |
| 超限警告 | 提示"误评高难度"，引导重估 | 立即流转或重估 | 严守流程纪律，禁止停留 |
| hardStop | 停止+流转+可重估 | 停止+必须流转 | 停止+必须流转+纪律不可破 |

> 前提：状态集开放（`getAllowedTargets` 按难度开放路径）已是难度自适应的主体；提示词只做配套。

### 方向 A：START 引导如实评估难度（治空转）

空转根源是**难度虚高**（简单任务误评 COMPLEX → 状态集全开、轮次上限虚高）。START 引导强调如实评估：

```
调用 set-task-info 时如实评估任务难度：
- 简单任务选 TRIVIAL/SIMPLE → 状态机自动走最短路径（直达 EXECUTE），不浪费轮次
- 复杂任务选 COMPLEX+ → 状态机全流程推进，保证质量
- 误评高难度会导致状态集全开、轮次上限虚高 → 空转
```

| 难度档 | 措辞 |
|:--|:--|
| TRIVIAL/SIMPLE | `完成后可流转`（宽松，与最短路径匹配） |
| MODERATE | `完成后必须流转` |
| COMPLEX+ | `必须流转，未流转请说明原因`（强烈，防跑偏；延后确认，措辞以 8/4 讨论为准） |

简单任务超限 → 温和（"建议重估难度"，因为可能是难度虚高）；复杂任务超限 → 严厉（"流程纪律"）。

## 第八部分：统一实施顺序与验收标准

### 实施顺序（无冲突版，2026/8/1 梳理）

**依赖链**：`types.ts` → `state-machine.ts` → `templates.ts` → `index.ts`（后者依赖前者类型/逻辑）。

**冲突规避三原则**：
1. 同文件多处改动**合并为一次连续改造**（templates 的 START/END + 指令强化 + 输出精简 + pathAdapter 一次完成）
2. index.ts 分两步：**先骨架后强化**（状态机逻辑是基础，指令强化是叠加）
3. 每步结束独立验证（不依赖未完成的其他文件）

```
步骤 0：备份 src/（防御性，可回退）

步骤 1：types.ts —— 状态定义（基础）
  ├─ ThinkingState: "IDLE" → "START" | "END"（含四业务态）
  ├─ STATE_META / STATE_MAX_TURNS（START/END maxTurns=1）/ FLOW_DIAGRAM / getMaxStateTurns
  ├─ SessionState 增 visited: ThinkingState[]
  └─ ✅ 单测：getMaxStateTurns 各状态/难度/空难度分支

步骤 2：state-machine.ts —— 状态机逻辑（依赖 1）
  ├─ DEFAULT_STATE（state 空/null）
  ├─ getAllowedTargets：START 替代 IDLE 出口；VERIFY 出口增 END；END 无合法出口
  ├─ transition：START 出发 +1、转入 END 清空画像、END 拒绝、记录 visited
  ├─ bumpAndWarn：超限分级（> maxTurns 警告 / > maxTurns+1/3 缓冲 hardStop）
  ├─ classifyTargets / formatNextStateHint 同步
  └─ ✅ 单测：getAllowedTargets 全难度出口；transition 成功/拒绝/END 拒绝/visited 记录；
        bumpAndWarn 三级阈值；setTaskInfo 仅 START；classifyTargets/formatNextStateHint

步骤 3：templates.ts —— 提示词一次性改造（依赖 1/2，合并 B3+C1+E3）
  ├─ IDLE 分支 → START 分支（含输出精简要求）；新增 END 分支（极简）
  ├─ 阶段目标前置 + actions must 措辞（强烈不强制）
```

### 验收标准

1. 新会话默认状态为 START（非 IDLE）
2. before_agent_start：END → START 自动转换；非 END 保持 + 续作提醒
3. 模型在 END 调用 transition 被拒绝
4. VERIFY 完成后进入 END，画像清空
5. turn_end 计数逻辑统一：START 参与计数（maxTurns=1，**超过（>）才警告**：第 1 轮正常，第 2 轮未流转才提示）；END 无 LLM 轮次自然不触发
6. 超限强制停止生效：`turnCount > maxTurns + max(1, ceil(maxTurns/3))`（超 1/3 缓冲）时注入 `<hardStop>` 强制停止指令（禁止工具调用与输出，必须流转）；仅超 maxTurns 时第一级警告
6. 难度如实评估生效：简单任务设 TRIVIAL/SIMPLE 走最短路径，复杂任务全流程（**非**"直接回答旁路"）
7. 旧会话 load 无异常（旧 `IDLE` 值原样加载，before_agent_start 检测后转 START）
8. 请求序列严格纯递增：相邻请求前者是后者前缀（`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 观测）
9. 行为指标：完成阶段职责后调用 transition 比例提升；工具循环内不再"做完直接总结跳过流转"
10. 全链路路径感知生效：直达 EXECUTE 时提示词为直达版（无"按方案执行"断档，整体适配路径）

| 风险 | 控制 |
